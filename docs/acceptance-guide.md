# 验收指南

本指南适用于新电脑接入检查和日常任务验收。程序测试、客户端连接、实际交付和人工批准是不同的检查层级，应分别记录。

## 1. 程序回归

在项目根目录执行：

```powershell
node --version
npm test
```

Node.js 需为 24 或更高版本。测试使用临时数据库和本机动态端口，覆盖状态机、显式租约、目录互斥、暂停、失联与重启恢复、HTTP 请求限制，以及双角色 MCP 交接和取消/EOF 等协议行为。

通过条件：测试无失败，命令退出码为 0。这只能证明程序回归通过。

## 2. 当前电脑接入

1. 启动工作台，打开“应用接入”，复制当前实例生成的配置。
2. 分别在 Codex 与 WorkBuddy 国内版中安装并启用 MCP 服务，完成应用自身要求的信任流程。
3. 必要时重新加载 MCP 或打开新会话，在目标聊天中主动请求调用 list_tasks。
4. 确认返回的是当前实例的项目和任务；空列表也可能是正常结果，因为每个角色只看到其可处理的任务。
5. 在存在任务时，再调用 get_task 读取该任务的交接包。

可辅助执行 `node scripts/check-integrations.mjs`。它仅提供脱敏的只读配置与服务诊断；桥最近在线不能证明模型正在推进任务。

## 3. 最小真实交接

选用单独的测试项目目录，写清一个可独立检查的目标，例如创建一个具有指定文本内容的文件。不要把真实业务文件作为首次接入试验对象。

1. 在工作台登记该测试目录并新建任务，写明文件名、精确内容、编码和禁止修改的范围。
2. 在 Codex 中要求领取任务并制定计划。保存本轮 claim_task 返回的 leaseId；显式 heartbeat 后 submit_plan。
3. 检查任务进入 ready，再在 WorkBuddy 中要求领取该任务并按计划实施。
4. WorkBuddy 使用自己本轮领取的新 leaseId，在每个实施步骤前显式 heartbeat；完成后先停止相关写入与子任务，再 submit_result。
5. 检查任务进入 review、owner=null，并独立检查实际文件内容和变更范围。

暂停、阻塞修订、断连恢复和多轮复杂项目需要另行实测，不能由这一次最小交接推定完成。

## 4. 如何判断“待验收”是否完成

逐项对照创建任务时的验收标准：

| 检查项 | 要看什么 |
|---|---|
| 成果存在 | 实际文件、页面或运行结果确实可访问 |
| 目标符合 | 每条验收标准均有对应证据；必要时亲自重跑检查 |
| 修改范围 | 变更文件符合计划，没有夹带无关修改 |
| 验证可信 | 检查命令、退出码与输出对应实际交付版本 |
| 执行已停止 | 客户端已交接，无继续写入的相关任务或子进程 |
| 剩余问题 | 未通过、未执行和不确定的检查被明确记录 |

所有必要条件满足后，在工作台填写人工验收说明并批准，任务才会从 review 进入 done。提交结果中的“已完成”或测试文本不能替代独立检查。

若成果需要修改，可修订计划继续实施；如果需要 Codex 接手，先确认外部执行已经停止，再使用工作台相应操作。不要在结果不确定时重复领取或重复提交，也不要复用旧 leaseId。

## 5. 验收记录模板

记录保存在本地，不将任务内容、租约、令牌、客户端配置或个人路径直接上传到公开仓库。

```text
日期：
验证层级：程序回归 / 工具加载 / 真实任务 / 人工验收
任务目标和验收标准：
客户端及版本：
开始状态与结束状态：
实际交付与变更文件：
检查命令、退出码与结果：
通过项：
失败项 / 未执行项 / 不确定项：
人工决定和说明：
```

数据备份需在服务停止后复制整个 data 目录。验收记录不包含完整代码快照；项目代码应另外使用 Git 管理。
